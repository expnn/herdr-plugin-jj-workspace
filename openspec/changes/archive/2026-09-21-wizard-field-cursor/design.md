## Context

现状（动机见 proposal.md）：

- 三处文本输入（wizard name、wizard base、remove 对话框 commit message）都是 `String` + 隐式末尾光标：编辑只有 `push`/`pop`（`src/main.rs:117-151`、`2210-2232`、`4176-4185`），事件循环把 `←` `→` `Home` `End` `Delete` 一律丢弃（`src/main.rs:2233`）。
- name 字段另有 `NameEditState{Fresh,Prefixed,Free}` 三态自动机：组件级操作只在锚点态生效，`Free` 态定义为逐字符追加/删除。原 change（`openspec/changes/archive/2026-09-10-workspace-name-edit`）的 D2 明确：锚点态删除安全的前提是"被删内容是自动生成的、无用户手输信息"，一旦用户开始编辑就必须退回逐字符，避免"改错一位却整删 slug"的破坏性行为。本设计的光标契约必须延续这条安全论证。
- 既有 8 条状态机单元测试通过纯函数 `apply_name_key` 驱动（`src/main.rs:5656-5735`），是可复用的测试形态。

## Goals / Non-Goals

**Goals:**

- 一个共享的单行光标编辑原语，三处输入框复用；行为可被纯函数测试覆盖。
- 光标与 name 锚点态的交互契约只有一条规则，状态组合最少。
- 现有锚点态组件级语义与 `Fresh + 字符输入` 的快捷替换流程零行为回归。

**Non-Goals:**

- 不做词级跳转（`Ctrl+←/→`）、不做 `Ctrl+U/K/W` 等 readline 绑定。
- 不做多行编辑、不做撤销/重做、不做鼠标点击定位。
- 不追求 grapheme cluster 级光标正确性（不引入 `unicode-segmentation` 依赖）。
- 不改 hint 文案、按钮布局、`valid_branch` 提交校验、名称生成与 base 解析链。

## Decisions

### D1: 光标用 char 下标显式建模，替代隐式末尾

字段新增 `cursor: usize`（字符下标，非字节）。插入/删除在光标处发生，渲染把块字符插到光标边界。

- 备选：字节下标——多字节字符（用户可输入 CJK/emoji）下插入会切坏 UTF-8 边界，否决。
- 备选：grapheme 下标——正确性更好但需新依赖，且提交校验只放行 ASCII，收益不匹配成本，否决。
- 初始光标在末尾；Tab 切换字段保留各自光标位置（标准表单行为）。备选"每次聚焦重置到末尾"否决：用户在 name/base 间来回核对时位置丢失。

### D2: 锚点态遇到任意导航键立即进入 Free（定案方案 A）

`←` `→` `Home` `End` `Delete` 任一按下：SHALL NOT 修改文本，SHALL 进入 Free（不比较光标是否实际位移，规则单一）。此后 Backspace 恒为逐字符。

- 备选 B（锚点态忽略导航键）：默认名 `workspace/<slug>` 永远无法原地编辑，首次按 `←` 无反应——把问题推迟而非解决，否决。
- 备选 C（不改状态，锚点操作仅当光标在末尾时生效）：`←`×3 再 `→`×3 回到末尾后 Backspace 又变回整删 slug，重新武装了 D2 要防的破坏性操作，否决。
- 关键取舍：导航键本身无视觉状态提示（锚点退出是隐式的）。接受——安全阀方向是"更早失效"，最坏后果是用户得到逐字符删除（非破坏性），而非相反。

### D3: 编辑原语收敛为共享的纯函数，状态机包在外层

引入一个共享的单行编辑表示（文本 + char 光标）与按键应用函数；name 的 `apply_name_key` 扩展为接收光标，或重构为 `LineEdit { text, cursor }` + `apply(key)`，name 状态机作为其外层包装：

- 锚点态（Fresh/Prefixed）的组件级分支仍走原逻辑，随后把光标重置到末尾；
- 进入 Free 后（含导航触发）全部按键委托给共享原语；
- base 与 commit message 直接使用共享原语，不携带状态机。

备选：三处各写一套键处理——重复且易漂移，否决。保留纯函数形态是为了延续既有 8 条测试的驱动方式。

### D4: 渲染保持"块字符插在光标 char 边界"

`format!("{pad}{before}█{after}")`，未聚焦不渲染；不改用反色单元格。

- 备选：反色/下划线单元格——更接近终端习惯，但需要按单元格改样式、改动现有渲染路径与视觉验收，收益仅是观感，否决。
- 已知边界：宽字符前插入 `█` 会让后续文本右移一列（正确，因为块占 1 列）；组合字符序列内落点可能不理想。提交校验只放行 `[A-Za-z0-9._/-]`，接受。

### D5: base 的替换锚点与导航

base 未编辑时的"首次按键替换整值"（`replace_on_type`）保留，但任意导航键按下即取消该语义且不修改文本、不置 dirty——与 D2 同构。备选：保持替换语义到首次文本编辑为止（按 `←` 后输入仍清空整值）——同类破坏性意外，否决。

### D6: hint 文案不变

wizard 的 `WIZARD_HINT` 与 remove 的 `COMMIT_HINT` 保持现有文案。规范层面 wizard 提示行只要求覆盖"输入/编辑、tab、提交、取消"，commit 子态 hint 未被枚举；加 `←→ move` 属发现性增强，可独立增量，不阻塞本次契约。

### D7: commit message 同批纳入

同一根因（无光标模型）的第三处输入，共享 D3 原语后边际成本小；不纳入会在同一插件内留下行为不一致。代价是 `workspace-removal-dialog` 多一条 delta requirement（已在 proposal 记录）。

## Risks / Trade-offs

- [锚点态退出无视觉提示] → 安全阀只会更早失效，最坏是逐字符删除（非破坏性）；接受。
- [现有 8 条状态机测试的调用签名变化] → 保持纯函数形态逐条迁移，行为断言不变；新增导航/光标用例。
- [宽字符/组合字符光标落点不理想] → 提交校验限制 ASCII 字符集；不引入新依赖，接受为已知边界。
- [长文本超宽] → 块字符插入使可见文本右移一列，超宽仍按现有 `Paragraph` 裁剪行为，无新增处理。
- [base 导航取消替换语义后用户预期不一致] → 与 name 的 D2 规则一致：导航即"我在编辑这段文本"，语义自洽。

## Migration Plan

纯交互行为变更，无配置/数据迁移；存量 workspace 名与 base 解析结果不受影响。回滚即还原三处键处理与渲染路径，无残留状态。
